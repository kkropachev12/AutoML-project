# Model Card: прогнозирование оттока клиентов

Карточка подготовлена по структуре Google [Model Cards for Model Reporting](https://research.google/pubs/model-cards-for-model-reporting/): сведения о модели, назначение, факторы, метрики, данные, результаты, этические аспекты и ограничения.

## 1. Сведения о модели — Model Details

| Поле | Описание |
| --- | --- |
| Название | Telco Customer Churn — AutoML Random Forest |
| Автор проекта | [kkropachev12](https://github.com/kkropachev12) |
| Дата карточки | 2 ноября 2026 года |
| Статус | Учебный прототип для офлайн-обучения и оценки |
| Задача | Бинарная классификация: `Churn = Yes` — клиент ушёл, `No` — остался |
| Модель | `RandomForestClassifier`, выбранный Optuna в эксперименте, описанном в README |
| Параметры | `n_estimators=140`, `max_depth=4`, `min_samples_split=3`, `min_samples_leaf=1` |
| Формат | `sklearn Pipeline`: подготовка признаков и классификатор |
| Артефакт | `artifacts/models/best_model.joblib`, создаётся при обучении и не хранится в Git |
| Версионирование | Код версионируется в Git; отдельный номер версии обученного артефакта не задан |
| Лицензия | Отдельная лицензия модели в репозитории не указана |

Числовые признаки обрабатываются через `SimpleImputer(strategy="median")` и `StandardScaler`, категориальные — через заполнение наиболее частым значением и `OneHotEncoder(handle_unknown="ignore")`. Параметры преобразований обучаются только на обучающей выборке.

Optuna сравнивает `LogisticRegression`, `RandomForestClassifier` и `GradientBoostingClassifier` по validation ROC-AUC. По умолчанию выполняются 20 попыток. При новом запуске может быть выбрана другая модель. Baseline — отдельная логистическая регрессия без AutoML-подбора.

Реализация: [AutoML](src/automl.py), [preprocessing](src/pipeline.py), [метрики](src/metrics.py). Описание эксперимента и параметры: [README](README.md).

## 2. Назначение — Intended Use

Модель оценивает риск оттока, чтобы аналитик или команда удержания могли ранжировать клиентов и выбрать кандидатов для персонального предложения, смены тарифа или дополнительной поддержки. В проекте реализованы обучение, оценка и сохранение модели; подключение к CRM и проведение кампаний относятся к предполагаемому применению.

Модель предназначена для учебных экспериментов и подготовки прототипа скоринга телеком-клиентов. Она не определяет причину ухода, не выбирает оптимальную скидку и не оценивает, изменит ли предложение поведение клиента. Горизонт будущего прогноза, например «уход в следующие 30 дней», в проекте отдельно не задан.

### Входные данные

Одна строка таблицы соответствует одному клиенту. После исключения `customerID` и `Churn` используются **19 признаков**:

| Группа | Признаки | Формат |
| --- | --- | --- |
| Демография | `gender`, `SeniorCitizen`, `Partner`, `Dependents` | Категории; `SeniorCitizen` — число 0 или 1 |
| Срок обслуживания | `tenure` | Число месяцев |
| Услуги | `PhoneService`, `MultipleLines`, `InternetService`, `OnlineSecurity`, `OnlineBackup`, `DeviceProtection`, `TechSupport`, `StreamingTV`, `StreamingMovies` | Категории исходного датасета |
| Договор и оплата | `Contract`, `PaperlessBilling`, `PaymentMethod` | Категории исходного датасета |
| Платежи | `MonthlyCharges`, `TotalCharges` | Числовые суммы в единицах исходных данных |

Перед обращением к сохранённому pipeline `TotalCharges` нужно привести к числу через `clean_data`; некорректные значения становятся пропусками. Затем передаётся таблица с теми же именами и типами признаков, что при обучении. Заполнение пропусков и кодирование выполняет pipeline.

При прогнозировании фактический `Churn` неизвестен и на вход не подаётся. `customerID` сохраняется отдельно для связывания результата с клиентом. Функция `prepare_data` предназначена для обучающих данных с целевой переменной, а не для новых клиентов без `Churn`.

### Выходные данные

- `predict_proba` возвращает оценки вероятностей классов; риск оттока берётся из столбца класса `Yes` с учётом `model.classes_`.
- `predict` возвращает класс `Yes` или `No`. Используется стандартное правило классификатора, без бизнес-подбора порога.
- Для предполагаемой передачи в CRM результат связывается с `customerID`: идентификатор клиента, оценка риска, предсказанный класс. Такая выгрузка пока не реализована.

Оценка вероятности находится в диапазоне от 0 до 1. Её калибровка не проверялась: значение 0,8 нельзя автоматически трактовать как гарантированные 80% уходов в аналогичной группе.

## 3. Факторы качества — Factors

Качество может зависеть от срока обслуживания, типа договора, подключённых услуг, размера платежей и изменения тарифов. Перенос на другую компанию или период требует отдельной проверки соответствия данных.

В данных есть `gender` и `SeniorCitizen`. Качество по этим группам, их пересечениям и бизнес-сегментам отдельно не измерялось. Общие метрики не подтверждают одинаковую точность для всех клиентов. Неизвестные категории технически обрабатываются encoder, но это не гарантирует качество прогноза для новых категорий.

## 4. Метрики — Metrics

Положительный класс — клиент с `Churn = Yes`.

| Метрика | Что показывает | Для чего используется |
| --- | --- | --- |
| ROC-AUC | Способность ранжировать ушедших клиентов выше оставшихся при разных порогах | Основной критерий выбора модели в Optuna |
| Accuracy | Долю всех правильных классификаций | Общая оценка; недостаточна сама по себе при дисбалансе классов |
| Precision | Долю действительно ушедших среди предсказанных уходов | Оценка доли потенциально лишних удерживающих контактов |
| Recall | Долю найденных клиентов среди всех действительно ушедших | Оценка числа пропущенных клиентов с оттоком |
| F1-score | Гармоническое среднее Precision и Recall | Совместная оценка двух типов ошибок |

Для baseline также сохраняются confusion matrix и ROC-кривая. Порог для кампании необходимо выбирать на validation-данных с учётом бюджета и стоимости ошибок; test используется для итоговой оценки. Финансовый эффект, калибровка и доверительные интервалы в текущем отчёте не рассчитаны.

## 5. Данные оценки — Evaluation Data

Оценка выполняется на отложенной части [Telco Customer Churn](data/telco_customer_churn.csv). При стандартных настройках:

- test — 20%, **1409 клиентов**;
- разделение стратифицировано по `Churn`, `random_state=42`;
- test не участвует в подборе гиперпараметров;
- validation для Optuna выделяется из оставшейся обучающей части: 25% от неё, **1409 клиентов**.

Это случайное разделение одного датасета. Проверок на независимой компании и на более позднем временном периоде нет.

## 6. Обучающие данные — Training Data

Источник в проекте — CSV Telco Customer Churn, обозначенный в README как датасет Kaggle / IBM Sample Data. Точная ссылка на исходную загрузку, версия и условия лицензии данных в репозитории не зафиксированы.

В файле **7043 клиента и 21 колонка**: 19 признаков, идентификатор и целевая переменная. Классы: **5174 `No` (73,5%)** и **1869 `Yes` (26,5%)**. В `TotalCharges` есть 11 пустых значений, которые при преобразовании становятся пропусками.

Во время AutoML-подбора обучение идёт на **4225 клиентах**, оценка кандидатов — на validation. Затем лучшая конфигурация переобучается на всей обучающей части из **5634 клиентов**. Baseline также обучается на 5634 клиентах. Медианы, масштабирование и категории encoder определяются только по соответствующей обучающей части. Балансировка классов в коде не применяется.

## 7. Количественные результаты — Quantitative Analyses

Результаты эксперимента из [README](README.md), оценка на test:

| Метрика | AutoML: Random Forest | Baseline: Logistic Regression |
| --- | ---: | ---: |
| ROC-AUC | 0,8371 | 0,8419 |
| Accuracy | 0,7892 | 0,8055 |
| Precision | 0,6860 | 0,6572 |
| Recall | 0,3797 | 0,5588 |
| F1-score | 0,4888 | 0,6040 |

Validation ROC-AUC выбранного Random Forest — **0,83497**. «Лучшая AutoML-модель» означает победителя среди попыток Optuna по validation ROC-AUC, а не превосходство над baseline на test.

Random Forest точнее среди положительных прогнозов, но находит около 38% ушедших клиентов; baseline — около 56%. В этом сравнении baseline лучше по ROC-AUC, Recall и F1-score. Для удержания клиентов выбор модели следует делать с учётом этих различий, а не только факта автоматического подбора.

## 8. Этические аспекты — Ethical Considerations

Ложноположительный прогноз может привести к ненужному контакту или расходу на предложение, ложноотрицательный — к упущенной возможности удержания. Демографические признаки могут влиять на распределение таких ошибок; перед практическим применением требуется анализ качества по группам.

Для бизнес-сценария решение о предложении остаётся за ответственным сотрудником. Оценка риска сама по себе не является основанием ухудшать условия обслуживания. При работе с реальными клиентами следует ограничивать доступ к персональным данным и сохранять связь с идентификаторами отдельно от признаков модели.

## 9. Ограничения и рекомендации — Caveats and Recommendations

- Модель проверена на одном учебном датасете. Переносимость на действующую клиентскую базу не подтверждена.
- Низкий Recall Random Forest означает значительную долю пропущенных уходов при стандартном решении классификатора.
- Для бизнес-прогноза нужно определить момент скоринга и горизонт оттока, используя только сведения, доступные до прогнозируемого события.
- Перед применением следует сравнить модель с baseline на актуальных данных, выбрать порог и оценить стоимость ошибок. Эффект предложений проверяется отдельным пилотом с контрольной группой.
- Feature importance показывает вклад признаков в модель, но не доказывает причины ухода.
- MLflow фиксирует эксперименты, а psutil — ресурсы обучения. Автоматический мониторинг дрейфа данных, производственных метрик и переобучение пока не реализованы.
